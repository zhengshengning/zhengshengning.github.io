## 1. GPU 核心架构

要理解 AI 计算的硬件基础，首先要搞清楚 GPU 内部的三个核心组件：SM、CUDA Core 和 Tensor Core。

### 1.1 SM（Streaming Multiprocessor，流多处理器）

SM 是 GPU 的基本计算单元，可以类比为 CPU 的一个核心（但比 CPU 核心简单得多）。你可以把每个 SM 想象成 GPU 里的一个"小工厂车间"——每个车间有自己的工人（CUDA Core、Tensor Core）、工具台（寄存器）和临时仓库（Shared Memory），多个车间并行开工，共同完成大规模计算任务。每个 SM 包含：

- 一组 CUDA Core（通用计算单元）
- 一组 Tensor Core（矩阵计算加速单元）
- 共享内存（Shared Memory）和 L1 Cache
- 寄存器文件（Register File）
- Warp 调度器

**一个 GPU 由多个 SM 组成**，SM 数量直接决定了 GPU 的并行计算能力：

| GPU | 架构 | SM 数量 |
|-----|------|---------|
| A100 | Ampere | 108 |
| H100 SXM | Hopper | 132 |
| H200 SXM | Hopper | 132 |
| B200 | Blackwell | 148 |

每个 SM 可以同时管理多个 **Warp**（32 个线程为一组），一个 SM 最多承载 64 个活跃 Warp（共 2048 个线程）。当一个 Warp 等待数据时，调度器可以切换到另一个 Warp 执行，从而隐藏访存延迟。

### 1.2 CUDA Core

CUDA Core 是 GPU 上的通用标量计算单元，每个 CUDA Core 在一个时钟周期内执行一次浮点或整数运算。CUDA Core 负责处理：

- FP32 单精度浮点运算
- FP64 双精度浮点运算（专用 FP64 单元）
- INT32 整数运算

CUDA Core 的计算范式是 **SIMT（Single Instruction, Multiple Threads）**：一条指令同时驱动 32 个线程（一个 Warp）执行相同操作，但各线程处理不同数据。

以 H100 为例：
- 每个 SM 包含 128 个 FP32 CUDA Core
- 132 个 SM 共计 16,896 个 CUDA Core
- FP32 峰值算力 = 16896 x 2 x 1830MHz = **~67 TFLOPS**

### 1.3 Tensor Core

Tensor Core 是专门为矩阵乘累加（MMA, Matrix Multiply-Accumulate）设计的加速单元。如果说 CUDA Core 是一个一个地算加减乘除的"计算器"，Tensor Core 则是一次能处理一整块矩阵的"批量计算引擎"。一条指令就可以完成一个小矩阵块的乘加运算（如 4x4、8x8 或 16x16），相比 CUDA Core 逐元素计算效率提升一个数量级。

Tensor Core 是大模型训练和推理的核心加速引擎。深度学习的核心操作——线性层（GEMM）和注意力（Attention）——本质上都是大规模矩阵乘法，天然适配 Tensor Core。

**Tensor Core 的演进**：

| 架构 | 支持精度 | 关键特性 |
|------|---------|---------|
| Volta (V100) | FP16 | 首次引入 Tensor Core |
| Ampere (A100) | FP16, BF16, TF32, INT8, INT4 | 支持稀疏（2:4 Structured Sparsity，算力翻倍） |
| Hopper (H100) | FP16, BF16, TF32, FP8, INT8 | 引入 FP8，支持 Transformer Engine 自动精度切换 |
| Blackwell (B200) | FP16, BF16, TF32, FP8, FP4, INT8 | 引入 FP4，第五代 Tensor Core |

**以 H100 SXM 为例，不同精度下的峰值算力**：

| 精度 | 算力 (TFLOPS) | 稀疏加速后 (TFLOPS) |
|------|:------------:|:------------------:|
| FP64 | 34 | - |
| FP32 (CUDA Core) | 67 | - |
| TF32 (Tensor Core) | 495 | 989 |
| BF16 / FP16 (Tensor Core) | 989 | 1,979 |
| FP8 (Tensor Core) | 1,979 | 3,958 |

关键结论：**Tensor Core FP8 算力是 CUDA Core FP32 算力的 ~60 倍**。这就是为什么现代大模型训练几乎完全依赖 Tensor Core，并积极采用低精度（BF16/FP8）训练。

### 1.4 三者的协作关系

```
GPU
├── SM 0
│   ├── CUDA Cores (128个) ── 通用标量运算 (FP32/INT32)
│   ├── Tensor Cores (4个)  ── 矩阵乘累加 (GEMM/Attention)
│   ├── Shared Memory / L1 Cache ── 片上高速缓存
│   ├── Register File ── 每线程私有寄存器
│   └── Warp Schedulers ── 线程调度
├── SM 1
│   └── ... (同上)
├── ...
├── SM 131 (H100共132个SM)
├── L2 Cache (50MB, 全局共享)
└── HBM3 (80GB, 显存)
```

简单记忆：
- **SM** 是调度和资源管理的基本单位
- **CUDA Core** 负责通用的逐元素计算（激活函数、LayerNorm、Softmax 等）
- **Tensor Core** 负责大规模矩阵乘法（线性层、Attention，占训练/推理 80%+ 时间）

## 2. 存储层次结构

GPU 的存储层次与 CPU 类似，遵循"越快越小越贵"的原则。理解存储层次是优化 CUDA 程序的基础。

### 2.1 各层存储的特性

```
寄存器 (Registers)
  │  最快，每线程私有，~0 cycle 延迟
  ▼
共享内存 (Shared Memory)
  │  片上 SRAM，同一 Block 内线程共享，~20-30 cycles
  ▼
L1 Cache
  │  与 Shared Memory 共享物理空间，自动管理
  ▼
L2 Cache
  │  全局共享，所有 SM 可访问，~200 cycles
  ▼
HBM (High Bandwidth Memory)
  │  "显存"，可以理解为GPU的"高速仓库"——容量大但取货也需要时间，~400-600 cycles
  ▼
主机内存 (Host Memory / CPU DRAM)
     需要通过 PCIe/NVLink 传输，延迟极高
```

### 2.2 关键参数对比（以 H100 SXM 为例）

| 存储层级 | 容量 | 带宽 | 延迟 | 访问范围 |
|---------|------|------|------|---------|
| 寄存器 | 每 SM 256KB | ~20 TB/s | ~0 cycle | 每线程私有 |
| 共享内存 | 每 SM 最多 228KB | ~20 TB/s | ~20-30 cycles | Block 内共享 |
| L1 Cache | 与共享内存共享 | ~20 TB/s | ~30 cycles | 每 SM |
| L2 Cache | 50MB | ~12 TB/s | ~200 cycles | 全局共享 |
| HBM3 | 80GB | 3.35 TB/s | ~400-600 cycles | 全局共享 |
| CPU DRAM | 数百GB-数TB | ~100 GB/s | 数千 cycles | 需 PCIe 传输 |

**几个关键数字要牢记**：

- 寄存器/共享内存的带宽比 HBM 高 **~6 倍**
- HBM 到共享内存的延迟差距约 **20 倍**
- HBM 到 CPU DRAM 还要跨 PCIe，带宽再降 **~50 倍**

### 2.3 对 AI 工作负载的影响

理解存储层次对优化 AI 工作负载至关重要：

- **模型权重** 存放在 HBM 中，推理时需要反复从 HBM 读取
- **KV Cache** 存放在 HBM 中，自回归生成时每步都要读写
- **FlashAttention** 的核心思想：通过 tiling 将数据分块搬到 Shared Memory 中计算，减少对 HBM 的读写次数
- **算子融合** 的本质：将多个小操作合并，避免中间结果写回 HBM 再重新读取

## 3. Memory Wall：为什么带宽比算力更致命

### 3.1 什么是 Memory Wall

Memory Wall（内存墙）是指**计算速度的增长远快于内存带宽的增长**，导致处理器经常"饿着肚子等数据"。打个比方：就像超市收银台处理速度很快，但后面补货跟不上，收银员只能干等货架填满。

用一个直观的类比：计算单元像一个食量惊人的大胃王（每秒吃掉数百 TFLOPS 的数据），而 HBM 带宽是食物传送带的速度。如果传送带跟不上，大胃王再厉害也只能干等。

### 3.2 用数据说话

以 H100 SXM 为例，计算 **Arithmetic Intensity**（计算强度）的平衡点：

```
FP16 Tensor Core 峰值算力 = 989 TFLOPS
HBM3 带宽 = 3.35 TB/s

平衡点 = 989 TFLOPS / 3.35 TB/s ≈ 295 FLOP/Byte
```

这意味着：**每从 HBM 读取 1 字节数据，需要完成 295 次 FP16 浮点运算，才能让计算单元不空闲。**

对比常见 AI 操作的实际计算强度：

| 操作 | 计算强度 (FLOP/Byte) | 瓶颈 |
|------|:--------------------:|------|
| 大矩阵 GEMM (M,N,K 都很大) | 数百~数千 | Compute Bound |
| 小矩阵 GEMM (Batch=1 推理) | 数十 | **Memory Bound** |
| Attention (长序列 Prefill) | 数百 | Compute Bound |
| Attention (Decode, 逐 token) | <10 | **Memory Bound** |
| 逐元素操作 (ReLU, LayerNorm) | 1-10 | **Memory Bound** |

**关键洞察**：

- 大模型 **训练** 阶段，由于 batch size 较大，大部分 GEMM 是 compute bound
- 大模型 **推理** 的 decode 阶段，每次只生成一个 token，batch 维度小，几乎所有操作都是 **memory bound**
- 这就是为什么推理优化（FlashAttention、KV Cache 管理、量化）本质上都在"少搬数据"

### 3.3 Roofline Model

Roofline Model 是判断一个 kernel 瓶颈在"算力"还是"带宽"的标准工具：

```
性能上限 (FLOPS)
    │
    │                    ┌─────── Compute Bound 区域
    │                  ╱  (算力是瓶颈)
    │                ╱
    │              ╱  ← 拐点：计算强度 = 算力/带宽
    │            ╱
    │          ╱
    │        ╱  Memory Bound 区域
    │      ╱    (带宽是瓶颈)
    │    ╱
    │  ╱
    │╱
    └──────────────────── 计算强度 (FLOP/Byte)
```

- **拐点左侧**：Memory Bound，优化方向是减少数据搬运（算子融合、量化、Tiling）
- **拐点右侧**：Compute Bound，优化方向是提高计算效率（用 Tensor Core、提高 Occupancy）

## 4. 主流 GPU 规格对比

### 4.1 数据中心 GPU 规格一览

| 指标 | A100 SXM | H100 SXM | H200 SXM | B200 SXM |
|------|:--------:|:--------:|:--------:|:--------:|
| **架构** | Ampere | Hopper | Hopper | Blackwell |
| **工艺** | 7nm | 4nm | 4nm | 4nm |
| **SM 数量** | 108 | 132 | 132 | 148 |
| **FP32 算力** | 19.5 TFLOPS | 67 TFLOPS | 67 TFLOPS | 90 TFLOPS |
| **FP16 Tensor** | 312 TFLOPS | 989 TFLOPS | 989 TFLOPS | 2,250 TFLOPS |
| **FP8 Tensor** | - | 1,979 TFLOPS | 1,979 TFLOPS | 4,500 TFLOPS |
| **显存类型** | HBM2e | HBM3 | HBM3e | HBM3e |
| **显存容量** | 80GB | 80GB | 141GB | 192GB |
| **显存带宽** | 2.0 TB/s | 3.35 TB/s | 4.8 TB/s | 8.0 TB/s |
| **NVLink 带宽** | 600 GB/s | 900 GB/s | 900 GB/s | 1,800 GB/s |
| **TDP** | 400W | 700W | 700W | 1000W |

### 4.2 关键趋势

**算力增长 vs 带宽增长**：

| 指标 | A100 → H100 | H100 → B200 |
|------|:-----------:|:-----------:|
| FP16 算力增长 | 3.2x | 2.3x |
| HBM 带宽增长 | 1.7x | 2.4x |
| 显存容量增长 | 1.0x (80→80GB) | 2.4x (80→192GB) |
| NVLink 带宽增长 | 1.5x | 2.0x |

几个值得关注的点：

1. **H200 vs H100**：相同架构，但 HBM3e 让显存容量从 80GB 增至 141GB，带宽从 3.35 升至 4.8 TB/s。对于 memory bound 的推理场景，H200 的提升比纸面算力差距更大
2. **显存容量越来越重要**：70B 参数模型 FP16 需要 ~140GB 显存，A100/H100 单卡放不下，H200 勉强可以，B200 有余量
3. **NVLink 带宽增长与算力同步**：保证多卡并行时通信不成为瓶颈

### 4.3 如何选择 GPU

| 场景 | 推荐 | 原因 |
|------|------|------|
| 大模型训练 (>100B) | H100/B200 + NVLink | 需要高算力 + 高带宽互联 |
| 大模型推理 (高吞吐) | H200/B200 | 更大显存 + 更高 HBM 带宽 |
| 大模型推理 (低成本) | A100 / L40S | 性价比高 |
| 小模型 / 微调 | A100 / H100 PCIe | 按需选择 |

## 5. 单机内部通信：NVLink 与 NVSwitch

当一个模型需要多张 GPU 协同工作时，GPU 之间的数据传输速度就成了关键。

### 5.1 PCIe：传统互联方式

PCIe（Peripheral Component Interconnect Express）是 GPU 与 CPU、GPU 与 GPU 之间最基本的互联方式。

| PCIe 版本 | 单向带宽 (x16) | 双向带宽 (x16) |
|-----------|:-------------:|:-------------:|
| PCIe 4.0 | 32 GB/s | 64 GB/s |
| PCIe 5.0 | 64 GB/s | 128 GB/s |

对于大模型训练来说，PCIe 带宽远远不够。以张量并行为例，每一层的前向和反向传播都需要 AllReduce 操作，PCIe 的带宽会严重拖慢训练速度。

### 5.2 NVLink：GPU 直连高速通道

NVLink 是 NVIDIA 专为 GPU 间通信设计的高速互联技术，绕过 PCIe 总线，让 GPU 之间直接通信。如果说 PCIe 是连接 GPU 的"普通公路"，那 NVLink 就是 GPU 之间的"直通高速公路"——不仅车道更多，限速也高好几倍。

**NVLink 演进**：

| NVLink 版本 | 所属架构 | 单链路带宽 | 每 GPU 链路数 | 每 GPU 总带宽 |
|------------|---------|:---------:|:-----------:|:------------:|
| NVLink 3.0 | Ampere (A100) | 50 GB/s | 12 | 600 GB/s |
| NVLink 4.0 | Hopper (H100) | 50 GB/s | 18 | 900 GB/s |
| NVLink 5.0 | Blackwell (B200) | 100 GB/s | 18 | 1,800 GB/s |

**对比 PCIe 5.0 x16 (64 GB/s)**：
- NVLink 4.0 (H100) 是 PCIe 5.0 的 **~14 倍**
- NVLink 5.0 (B200) 是 PCIe 5.0 的 **~28 倍**

### 5.3 NVSwitch：全连接交换网络

当机器内有 8 张 GPU 时，如果每两张卡之间都用 NVLink 直连，布线复杂度极高。NVSwitch 就是解决这个问题的交换芯片——相当于一个"高速公路立交枢纽"，所有 GPU 通过它互联，实现**任意两张卡之间的满带宽通信**，无需点对点逐一接线。

**DGX 系统拓扑示例（8x H100）**：

```
         ┌──────────────────────────────────┐
         │          NVSwitch x4             │
         │   (全交叉互联交换网络)            │
         └──┬───┬───┬───┬───┬───┬───┬───┬──┘
            │   │   │   │   │   │   │   │
          GPU0 GPU1 GPU2 GPU3 GPU4 GPU5 GPU6 GPU7

每对 GPU 之间通过 NVSwitch 互联：
  - 任意两卡间带宽：900 GB/s (NVLink 4.0)
  - 8 卡 AllReduce 聚合带宽：900 GB/s
```

**NVSwitch 的关键价值**：

- 消除拓扑瓶颈：无论哪两张卡之间通信，带宽都是满速
- 支持高效的 AllReduce：张量并行严重依赖 AllReduce，NVSwitch 保证了通信效率
- 这就是为什么**张量并行（TP）通常限制在单机内部**——只有 NVLink+NVSwitch 的带宽才能支撑层层的 AllReduce

### 5.4 实际查看 GPU 拓扑

在机器上执行以下命令可以查看 GPU 间的互联拓扑：

```bash
nvidia-smi topo -m
```

输出示例：

```
        GPU0  GPU1  GPU2  GPU3  GPU4  GPU5  GPU6  GPU7
GPU0     X    NV18  NV18  NV18  NV18  NV18  NV18  NV18
GPU1    NV18   X    NV18  NV18  NV18  NV18  NV18  NV18
GPU2    NV18  NV18   X    NV18  NV18  NV18  NV18  NV18
...
```

其中 `NV18` 表示通过 18 条 NVLink 连接，`PHB` 表示通过 PCIe Host Bridge 连接，`SYS` 表示跨 NUMA 节点。

## 6. 多机间通信：InfiniBand 与 RoCE

单机 8 卡是 AI 训练的基本单元，但训练百亿/千亿参数模型通常需要数十甚至数百台机器组成集群。此时多机间的网络互联成为关键。

### 6.1 为什么不用以太网？

传统以太网（TCP/IP）虽然成本低、普及广，但存在几个致命问题：

- **延迟高**：数据需要经过内核协议栈处理，延迟在 50-100 微秒级别
- **CPU 开销大**：数据拷贝和协议处理占用大量 CPU 资源
- **带宽受限**：即使是 100GbE，利用率也很难打满

大模型训练中，梯度同步是高频操作，每一步训练都要执行。高延迟和低带宽会直接拖慢训练速度。

### 6.2 RDMA：Remote Direct Memory Access

RDMA（远程直接内存访问）是解决上述问题的核心技术。它允许一台机器**直接读写另一台机器的内存，完全绕过 CPU 和操作系统内核**。打个比方：传统方式像寄快递，要经过前台收件、登记、分拣等层层手续；RDMA 则像两栋楼之间架了一条传送带，包裹直接从这边仓库送到那边仓库，谁都不用经手。

```
传统 TCP/IP：
  App → 系统调用 → 内核协议栈 → 数据拷贝 → 网卡 → 网络 → ... → 反向过程
  延迟: ~50-100μs

RDMA：
  App → 网卡(直接DMA) → 网络 → 网卡(直接DMA) → 远端内存
  延迟: ~1-2μs
```

RDMA 的三大优势：
- **零拷贝（Zero-Copy）**：数据不需要在用户态和内核态之间来回拷贝
- **内核旁路（Kernel Bypass）**：绕过操作系统内核，减少上下文切换开销
- **极低延迟**：端到端延迟降至微秒级

### 6.3 InfiniBand（IB）

InfiniBand 是目前 AI 训练集群中最主流的高性能网络方案，原生支持 RDMA。

**InfiniBand 速率演进**：

| 标准 | 单链路速率 | 4x 带宽 (常用) | 等效带宽 |
|------|:---------:|:-------------:|:--------:|
| FDR | 14 Gb/s | 56 Gb/s | 6.8 GB/s |
| EDR | 25 Gb/s | 100 Gb/s | 12.5 GB/s |
| HDR | 50 Gb/s | 200 Gb/s | 25 GB/s |
| NDR | 100 Gb/s | 400 Gb/s | 50 GB/s |
| XDR | 200 Gb/s | 800 Gb/s | 100 GB/s |

目前大型 AI 集群普遍采用 **NDR 400Gb/s (50 GB/s)** 或更新的 **XDR 800Gb/s**。

**InfiniBand 的特点**：

- 原生 RDMA 支持，协议栈高效
- 拥塞控制由硬件实现，对大规模集合通信友好
- 需要专用交换机和网卡（HCA），成本较高
- NVIDIA（收购 Mellanox 后）是主要供应商，生态完整

### 6.4 RoCE（RDMA over Converged Ethernet）

RoCE 是在以太网上实现 RDMA 的技术方案，让标准以太网硬件也能享受 RDMA 的低延迟优势。

| 版本 | 封装方式 | 特点 |
|------|---------|------|
| RoCE v1 | RDMA over Ethernet（二层） | 不可跨子网路由 |
| RoCE v2 | RDMA over UDP/IP（三层） | 可路由，更通用 |

**InfiniBand vs RoCE 对比**：

| 维度 | InfiniBand | RoCE v2 |
|------|-----------|---------|
| 延迟 | ~1 μs | ~2-5 μs |
| 带宽 | 400-800 Gb/s | 100-400 Gb/s |
| 拥塞控制 | 硬件原生，成熟 | 依赖 ECN/PFC 配置，需调优 |
| 成本 | 高（专用交换机） | 中（复用以太网基础设施） |
| 大规模集群稳定性 | 更好 | 需要精心调优 |
| 典型用户 | 大型 AI Lab | 云厂商、中小规模集群 |

**选型建议**：

- 如果追求极致性能和大规模稳定性（如万卡集群训练），选 **InfiniBand**
- 如果预算有限或需要复用现有网络基础设施，**RoCE v2** 是务实的选择
- 两者都支持 NCCL，上层训练代码基本无需修改

## 7. 集合通信原语

分布式训练的核心操作是让多张 GPU 之间交换数据。理解集合通信原语（Collective Communication Primitives），就能理解分布式训练中"数据是怎么流动的"。

### 7.1 五大核心原语

**Broadcast（广播）**

一个 GPU 将数据发送给所有其他 GPU：

```
发送前:        发送后:
GPU0: [ABCD]   GPU0: [ABCD]
GPU1: [    ]   GPU1: [ABCD]
GPU2: [    ]   GPU2: [ABCD]
GPU3: [    ]   GPU3: [ABCD]
```

用途：分发模型参数、共享配置。

**Reduce（归约）**

所有 GPU 的数据按元素聚合（如求和）到一个 GPU：

```
发送前:        Reduce(sum) 到 GPU0 后:
GPU0: [1,2,3]  GPU0: [10,20,30]
GPU1: [2,4,6]  GPU1: [2,4,6]    (不变)
GPU2: [3,6,9]  GPU2: [3,6,9]    (不变)
GPU3: [4,8,12] GPU3: [4,8,12]   (不变)
```

**AllReduce（全归约）**

所有 GPU 的数据归约后，结果分发给所有 GPU。等价于 Reduce + Broadcast，但实现上更高效。用大白话说就是：所有人先把各自的答案汇总求和，再把结果发给每个人——"先收作业算总分，再把成绩单发给全班"。

```
发送前:        AllReduce(sum) 后:
GPU0: [1,2,3]  GPU0: [10,20,30]
GPU1: [2,4,6]  GPU1: [10,20,30]
GPU2: [3,6,9]  GPU2: [10,20,30]
GPU3: [4,8,12] GPU3: [10,20,30]
```

用途：**数据并行训练中同步梯度**——每张卡计算各自的梯度，AllReduce 后所有卡拿到相同的平均梯度。

**AllGather（全收集）**

每个 GPU 持有数据的一个分片，收集后每个 GPU 都拥有完整数据：

```
发送前:       AllGather 后:
GPU0: [A]     GPU0: [A,B,C,D]
GPU1: [B]     GPU1: [A,B,C,D]
GPU2: [C]     GPU2: [A,B,C,D]
GPU3: [D]     GPU3: [A,B,C,D]
```

用途：ZeRO-3 中在前向传播前收集完整参数。

**ReduceScatter（归约分发）**

先归约，再将结果的不同分片分发到不同 GPU：

```
发送前:          ReduceScatter(sum) 后:
GPU0: [1,2,3,4]  GPU0: [10]      (第0个元素的归约结果)
GPU1: [2,3,4,5]  GPU1: [20]      (第1个元素的归约结果)
GPU2: [3,4,5,6]  GPU2: [30]      (第2个元素的归约结果)
GPU3: [4,5,6,7]  GPU3: [40]      (第3个元素的归约结果)
```

用途：ZeRO 系列中分布存储归约后的梯度/参数。

### 7.2 AllReduce 的高效实现：Ring AllReduce

**Ring AllReduce** 是分布式训练中最经典的 AllReduce 实现。N 个 GPU 排成一个逻辑环，算法分为两个阶段：

**第一阶段：ReduceScatter（N-1 步）**

每步中，每个 GPU 向下一个 GPU 发送一个 chunk，同时从上一个 GPU 接收并累加。N-1 步后，每个 GPU 持有最终结果的 1/N。

**第二阶段：AllGather（N-1 步）**

每步中，每个 GPU 将持有的最终 chunk 向下一个 GPU 传递。N-1 步后，每个 GPU 都持有完整结果。

**通信量分析**：

```
每个 GPU 的发送量 = 2 × (N-1)/N × 数据量
```

当 N 较大时，每个 GPU 的通信量趋近于 **2 倍数据量**，与 GPU 数量无关。这意味着 Ring AllReduce 可以有效利用所有链路的带宽。

### 7.3 集合通信与并行策略的对应关系

| 并行策略 | 主要通信原语 | 通信频率 | 通信量 |
|---------|------------|---------|--------|
| 数据并行 (DDP) | AllReduce | 每层反向传播后 | 梯度大小 |
| ZeRO-1/2 | AllReduce / ReduceScatter | 每层反向传播后 | 梯度大小 |
| ZeRO-3 | AllGather + ReduceScatter | 每层前向+反向 | 参数大小 |
| 张量并行 (TP) | AllReduce / AllGather | 每层前向+反向 | 激活大小 |
| 流水线并行 (PP) | 点对点 Send/Recv | 每个 micro-batch | 激活大小 |

## 8. NCCL：GPU 集合通信库

### 8.1 什么是 NCCL

NCCL（NVIDIA Collective Communications Library，发音 "Nickel"）是 NVIDIA 开发的多 GPU 集合通信库。它是 PyTorch、DeepSpeed、Megatron-LM 等所有主流深度学习框架的底层通信引擎。

NCCL 的核心能力：

- 自动检测 GPU 拓扑（NVLink、PCIe、IB），选择最优的通信路径和算法
- 支持所有核心集合通信原语（AllReduce、AllGather、ReduceScatter 等）
- 支持单机多卡和多机多卡场景
- 通信与计算可重叠（overlap），隐藏通信延迟

### 8.2 NCCL 的通信后端

NCCL 支持多种底层传输方式，会根据硬件拓扑自动选择：

| 传输方式 | 适用场景 | 说明 |
|---------|---------|------|
| NVLink / NVSwitch | 单机卡间通信 | 最高带宽，优先使用 |
| PCIe P2P | 单机卡间通信（无 NVLink） | 带宽低于 NVLink |
| InfiniBand Verbs | 多机间通信 | RDMA，低延迟高带宽 |
| RoCE | 多机间通信 | 以太网上的 RDMA |
| Socket (TCP) | 回退方案 | 性能最差，仅用于兼容 |

### 8.3 在 PyTorch 中使用 NCCL

NCCL 是 PyTorch 分布式训练的默认通信后端：

```python
import torch.distributed as dist

# 初始化进程组，使用 NCCL 后端
dist.init_process_group(backend='nccl')

# 创建张量
tensor = torch.randn(1024, 1024, device='cuda')

# AllReduce：所有 GPU 的 tensor 求和
dist.all_reduce(tensor, op=dist.ReduceOp.SUM)

# AllGather：收集所有 GPU 的 tensor
tensor_list = [torch.zeros_like(tensor) for _ in range(dist.get_world_size())]
dist.all_gather(tensor_list, tensor)

# ReduceScatter
output = torch.zeros(256, 1024, device='cuda')  # 每个 GPU 分到 1/4
input_list = list(tensor.chunk(dist.get_world_size()))
dist.reduce_scatter(output, input_list, op=dist.ReduceOp.SUM)
```

### 8.4 NCCL 常用环境变量

在调试和优化分布式训练时，以下环境变量非常有用：

```bash
# 打印 NCCL 调试信息（看到选择了什么拓扑和算法）
export NCCL_DEBUG=INFO

# 更详细的调试信息（含通信图和带宽）
export NCCL_DEBUG=TRACE

# 指定使用的网络接口（多网卡时有用）
export NCCL_SOCKET_IFNAME=eth0

# 指定 IB 设备
export NCCL_IB_HCA=mlx5_0

# 禁用特定传输方式（调试用）
export NCCL_P2P_DISABLE=1        # 禁用 P2P (NVLink/PCIe)
export NCCL_SHM_DISABLE=1        # 禁用共享内存

# 设置通信缓冲区大小
export NCCL_BUFFSIZE=16777216    # 16MB
```

### 8.5 NCCL 性能分析

使用 NVIDIA 提供的 `nccl-tests` 工具测试实际通信带宽：

```bash
# 编译 nccl-tests
git clone https://github.com/NVIDIA/nccl-tests.git
cd nccl-tests
make MPI=1 MPI_HOME=/usr/local/mpi CUDA_HOME=/usr/local/cuda NCCL_HOME=/usr/local/nccl

# 单机 8 卡 AllReduce 带宽测试
./build/all_reduce_perf -b 8 -e 256M -f 2 -g 8

# 多机测试（通过 MPI 启动）
mpirun -np 16 --hostfile hosts \
  -x NCCL_DEBUG=INFO \
  -x NCCL_IB_HCA=mlx5_0 \
  ./build/all_reduce_perf -b 8 -e 256M -f 2 -g 8
```

输出示例解读：

```
#       size    count    type   redop     time   algbw   busbw
         8B        2   float     sum    25.43    0.00    0.00
       256B       64   float     sum    26.12    0.01    0.02
      64KB    16384   float     sum    28.78    2.22    3.89
      16MB  4194304   float     sum    95.20  168.07  294.12
     256MB 67108864   float     sum   743.4   344.2   602.4
```

- `algbw`：算法带宽 = 数据量 / 时间
- `busbw`：总线带宽 = algbw * 2(N-1)/N，反映实际硬件链路利用率

**经验参考值**（8x H100 SXM 单机 AllReduce）：
- busbw 应接近 **~850 GB/s**（NVLink 4.0 理论 900 GB/s 的 ~95%）
- 如果远低于此值，需要检查 NVLink 拓扑或 NCCL 配置

## 9. 从硬件视角理解分布式训练瓶颈

掌握了硬件和通信基础，我们可以从物理层面理解分布式训练的常见瓶颈。

### 9.1 张量并行（TP）为什么限制在单机

张量并行在每一层的前向和反向传播中都需要 AllReduce。以一个 Transformer 层为例：

```
前向: 输入 → Linear1 → AllReduce → 激活 → Linear2 → AllReduce → 输出
反向: 梯度 → AllReduce → Linear2 → AllReduce → Linear1 → ...
```

每层 4 次 AllReduce，一个 80 层的模型意味着 320 次 AllReduce。如果走 IB 网络（~50 GB/s），而不是 NVLink（~900 GB/s），通信延迟会增加 **18 倍**，训练速度将断崖式下降。

### 9.2 数据并行的通信量分析

数据并行中，AllReduce 的通信量 = 模型参数量：

| 模型参数 | FP16 梯度大小 | 8 卡 AllReduce 通信量 (每卡) | NVLink 4.0 耗时 |
|---------|:------------:|:--------------------------:|:--------------:|
| 7B | 14 GB | ~28 GB | ~31 ms |
| 70B | 140 GB | ~280 GB | ~311 ms |

如果跨机走 IB 网络，70B 模型的 AllReduce 耗时会变为 ~5.6 秒，严重影响训练效率。这就是为什么 ZeRO 系列要切分梯度和参数——用更多次小通信替代一次大通信。

### 9.3 流水线并行的气泡问题

流水线并行将模型按层切分到不同机器，机器间通过 Send/Recv 传递激活值。通信量远小于 TP 和 DP，但面临**流水线气泡（Pipeline Bubble）**问题：

```
时间 →
GPU0: [F1][F2][F3][F4][  ][  ][  ][  ][B4][B3][B2][B1]
GPU1: [  ][F1][F2][F3][F4][  ][  ][B4][B3][B2][B1][  ]
GPU2: [  ][  ][F1][F2][F3][F4][B4][B3][B2][B1][  ][  ]
GPU3: [  ][  ][  ][F1][F2][F3][B3][B2][B1][  ][  ][  ]
         ↑空闲等待（气泡）
```

气泡占比 = (P-1) / (P-1+M)，其中 P 是流水线级数，M 是 micro-batch 数量。增大 M 可以减小气泡，但会增大显存占用。

### 9.4 常见瓶颈排查思路

| 现象 | 可能原因 | 排查方法 |
|------|---------|---------|
| 训练速度远低于预期 | 通信带宽不足 | `nccl-tests` 测带宽 |
| GPU 利用率低 | 数据加载瓶颈 / CPU 预处理慢 | Nsight Systems 看 CPU-GPU 交互 |
| 某些卡比其他卡慢 | NVLink 拓扑不对称 | `nvidia-smi topo -m` |
| 多机扩展效率差 | IB 网络配置有问题 | `NCCL_DEBUG=INFO` 看传输路径 |
| 显存 OOM | KV Cache / 激活 / 优化器状态 | 逐项计算显存占用 |
