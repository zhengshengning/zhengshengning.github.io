## 📖 本章概述

在讲任何并行策略之前，必须先回答一个最朴素的问题：**多张卡是怎么"组队"的，一条命令怎么把进程拉起来**。本章是整个系列的工程地基——读完能独立跑通一个最小多卡训练脚本，理解后续每一章默认的运行环境。

---

## 📑 章节结构

### 1. 单机单卡 → 单机多卡 → 多机多卡

- 三种规模的硬件拓扑与典型场景
- 进程模型：为什么 PyTorch 推荐"一卡一进程"（绕开 GIL、独占 CUDA 上下文）
- 概念地图：Node / Process / Rank / Local Rank / World Size 的关系

### 2. 核心概念：进程组（Process Group）

- `rank`：全局进程编号（0 ~ world_size-1）
- `local_rank`：节点内进程编号，决定绑定哪块 GPU（`torch.cuda.set_device(local_rank)`）
- `world_size`：参与训练的总进程数
- `init_process_group(backend, ...)`：建立通信组，`backend` 选择（NCCL=GPU、Gloo=CPU）
- 子通信组（subgroup）：TP/PP/DP 各自的通信域如何从全局组派生（为后续 3D 并行铺垫）

### 3. 启动方式演进：从 launch 到 torchrun

- 早期 `torch.distributed.launch`（已废弃）
- `torchrun` 的环境变量注入：`RANK` / `LOCAL_RANK` / `WORLD_SIZE` / `MASTER_ADDR` / `MASTER_PORT`
- 单机多卡启动：`torchrun --nproc_per_node=8 train.py`
- 多机多卡启动：`--nnodes` / `--node_rank` / `--rdzv_backend` / `--rdzv_endpoint`
- Rendezvous 机制：多机如何"会合"建立连接

### 4. NCCL 关键环境变量

- `NCCL_DEBUG=INFO`：排查通信问题的第一手段
- `NCCL_SOCKET_IFNAME` / `NCCL_IB_HCA`：指定网卡 / IB 设备
- `NCCL_P2P_DISABLE` / `NCCL_SHM_DISABLE`：调试用开关
- `CUDA_VISIBLE_DEVICES` 与 device 绑定的关系

### 5. 第一个多卡训练脚本（动手）

- 最小可运行模板：init → set_device → DDP 包裹 → 训练循环 → destroy
- 仅 rank 0 打印日志 / 保存模型的惯例
- 常见首次踩坑：端口占用、`MASTER_ADDR` 配置错、卡 hang 在 `init_process_group`
