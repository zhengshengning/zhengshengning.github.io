# Blog Post Generator

根据已有材料生成正式可发表的 Hexo 博客文章，输出到 `source/_posts/` 目录。

## 工作流程

### 1. 分析输入材料

读取用户提供的材料（文件路径、粘贴文本、URL 等），识别：
- 主题和核心内容
- 已有结构（标题、段落、代码等）
- 需要补充的部分（缺少引言、缺少总结、结构不完整等）

**原创性要求**：参考材料仅作为**主题和大纲的参考**，不得直接复制原文内容。具体要求：
- **提取骨架，重写血肉**：从参考材料中提取主题、知识点清单和章节结构，但所有正文段落、解释说明、代码示例、表格数据都必须用自己的语言重新组织和表述
- **禁止原文搬运**：不得整段复制参考材料的文字。即使表达同一个技术概念，也必须换一种说法、换一个角度、或换一组例子来讲解
- **代码示例独立编写**：代码不能直接照搬参考材料，应根据知识点自行编写有代表性的示例，或在原示例基础上做实质性修改（如换变量名、换场景、换实现方式）
- **增加独有价值**：在参考材料的基础上，补充自己的理解、实践经验、踩坑提示、性能对比、决策建议等原创内容，让文章有区别于原材料的独特价值

### 2. 确定分类和标签

根据内容匹配博客的分类体系，参考 [references/categories.md](references/categories.md) 中的分类映射表。若无法确定，询问用户。

**如果文章需要使用映射表中不存在的新分类**，必须同步更新 `references/categories.md`，添加新的分类行并填写适用主题和已有文章。

### 3. 补充和优化内容

按需执行：
- **补充引言段**：1-2 句话概括文章价值，紧跟 `<!-- more -->` 摘要分隔符
- **优化标题层级**：使用 `##` 作为主章节、`###` 作为子章节，可用编号 `## 1. 章节名`
- **章节标题 Emoji 图标美化**：为 `##` 级别标题添加 emoji 图标提升可读性。参考 [references/icons.md](references/icons.md) 中的图标库选择合适的 emoji。具体规则：
  - **编号标题不加 emoji**：带数字编号的标题（如 `## 1. 章节名`、`## 2.3 子章节`）保持原样，不添加 emoji
  - **非编号标题加 emoji**：没有数字编号的固定章节标题在文字前添加 emoji，格式为 `## 📑 目录`（emoji 与文字间一个空格）
  - **固定章节 emoji 映射表**：
    | 章节标题 | Emoji |
    |---------|-------|
    | 目录 | 📑 |
    | 总结 | 📝 |
    | 参考资料 | 📚 |
    | 自我检验清单 | 🎯 |
    | 快速参考卡片 | 📋 |
  - **其他非编号标题**：根据章节内容语义从 [references/icons.md](references/icons.md) 中选择最贴切的 emoji（如"背景"用 📖、"安装"用 ⚙️、"常见问题"用 ❓）
  - **`###` 及以下级别标题不加 emoji**
- **正文内容 Emoji 图标美化**：在正文的适当位置使用 emoji 增强可读性和视觉层次。参考 [references/icons.md](references/icons.md) 选择合适的 emoji。具体规则：
  - **表格表头图标**：对比类表格的列标题可加 emoji 突出语义，如 `| ✅ 优点 | ❌ 缺点 |`、`| 📊 指标 | 📝 含义 |`
  - **关键提示/注意事项**：段落开头用 emoji 标记提示类型：
    - 💡 提示/技巧：`💡 **提示**：...`
    - ⚠️ 警告/注意：`⚠️ **注意**：...`
    - 📌 重点/关键：`📌 **关键点**：...`
    - 🔑 核心概念：`🔑 **核心概念**：...`
  - **对比列表**：在对比项前用 emoji 区分正反，如 `✅ 推荐做法` / `❌ 不推荐做法`
  - **步骤流程**：可用 emoji 标记流程节点，如 `📥 输入 → ⚙️ 处理 → 📤 输出`
  - **使用原则**：
    - 适度使用，每个章节内容中 emoji 不超过 3-5 处，避免视觉干扰
    - 同类场景使用统一的 emoji（如所有"提示"都用 💡，不要混用）
    - 纯技术描述段落（定义、公式推导、代码讲解）不加 emoji
    - emoji 用于增强信息层次，不是装饰——每个 emoji 都应有明确的语义功能
- **补充缺失章节**：根据主题补充必要的背景介绍、步骤说明、代码示例、总结等
- **代码块规范化**：所有代码块加语言标识符（```python、```bash 等）
- **数学公式使用 LaTeX 格式**：文章中出现的数学公式必须使用 MathJax/LaTeX 语法，而不是代码块。行内公式用 `$...$`（如 `$O(N^2)$`），行间公式用 `$$...$$` 独占一行。具体规则：
  - 独立的数学表达式（如定义、推导步骤）使用 `$$...$$` 行间公式
  - 正文中嵌入的变量、符号、短表达式使用 `$...$` 行内公式
  - 矩阵运算、向量符号等用 LaTeX 命令：`\mathbb{R}`（实数集）、`\in`（属于）、`\times`（乘号）、`\cdot`（点乘）、`\odot`（逐元素乘）、`\top`（转置）、`\text{}`（文字标注）、`\frac{}{}`（分数）、`\sqrt{}`（根号）、`\quad`（间距）等
  - 多行公式使用 `\begin{aligned}...\end{aligned}` 环境
  - 伪代码和编程代码仍使用代码块（```），数学公式不要放在代码块里
  - **行间公式必须使用块级格式**：`$$` 必须独占一行，公式内容在中间行，不要写成单行 `$$ ... $$`。正确写法：
    ```
    $$
    E = mc^2
    $$
    ```
    错误写法：`$$ E = mc^2 $$`（单行格式可能被 Markdown 解析器干扰导致渲染失败）
  - **Hexo 下划线冲突**：Hexo 的 Markdown 渲染器会将 `_` 识别为斜体标记，当一个公式中出现**多个下划线**时（如 `\text{head}_1, \text{head}_2`），Markdown 会将相邻的 `_` 配对解释为斜体，导致 MathJax 无法正确渲染下标。**解决方法**：在 `$$` 块级公式中，如果同一行有多个下划线用于下标，必须将 `_` 转义为 `\_`。例如：
    - 错误：`\text{head}_1, \text{head}_2, \ldots, \text{head}_{32}`
    - 正确：`\text{head}\_1, \text{head}\_2, \ldots, \text{head}\_{32}`
    - 注意：单个下划线的简单公式（如 `$d_{model}$`、`$W_Q$`）通常不受影响，只有同一行出现多个 `_` 且可能被 Markdown 配对时才需要转义
- **格式统一**：列表用 `- `，粗体用 `**text**`，行内代码用反引号，表格用 pipe 语法
- **Hexo 加粗特殊字符转义**：Hexo 的 Markdown 渲染器在 `**...**` 加粗文本中遇到某些特殊字符时会解析异常，导致加粗失效或内容不显示。**解决方法**：在加粗文本内的特殊字符前加 `\` 转义。需要转义的字符包括：`?`、`~`、`%`、`*`、`[`、`]`、`(`、`)`、`#`、`+`、`!` 等。例如：
  - 错误：`**100% 利用率**`、`**为什么？**`、`**~4x 加速**`
  - 正确：`**100\% 利用率**`、`**为什么\？**`、`**\~4x 加速**`
  - 注意：纯中文和英文字母数字组成的加粗文本不受影响，只有包含上述特殊字符时才需要转义
- **补充参考资料**：如有引用来源，在末尾添加 `## 参考资料` 章节，每条参考资料必须附上可点击的链接，格式为 `- [资源名称](URL)`。对于论文优先使用 arXiv 链接，官方文档使用官网链接，开源项目使用 GitHub 链接。如果某条资料确实无法找到公开链接，可以省略链接但需标注来源
- **补充自我检验清单**：在参考资料之前添加 `## 🎯 自我检验清单` 章节，列出 5-10 条可量化的检验标准，读者学完本文后应该能做到的事情（用"能……"句式，如"能用 PyTorch DDP 将单卡脚本改为多卡训练"）

### 4. 生成 Frontmatter

```yaml
---
title: 文章标题
date: YYYY-MM-DD HH:mm:ss
mathjax: true        # 仅当文章包含数学公式时添加
categories:
  - [一级分类, 二级分类]
tags: [标签1, 标签2, 标签3]
---
```

规则：
- `date` 使用当前时间，格式 `YYYY-MM-DD HH:mm:ss`
- `mathjax`：扫描文章正文是否包含数学公式（`$$...$$` 行间公式或 `$...$` 行内公式），如果包含则在 frontmatter 中添加 `mathjax: true`，否则不添加此字段
- `categories` 必须使用数组嵌套语法 `- [Parent, Child]`，从分类映射表中选取
- `tags` 使用行内数组语法 `[Tag1, Tag2, ...]`，3-5 个标签

### 5. 输出文章

- 文件路径：`source/_posts/{标题}.md`（文件名即文章标题，中文直接使用）
- 必须包含 `<!-- more -->` 摘要分隔符（在引言段之后）
- 使用 Write 工具写入文件

### 6. 知识点正确性检查

文章写入文件后，调用 `/article-fact-checker` 对生成的文章进行知识点正确性审查：
- 检查事实性错误、不严谨表述、过时信息、数值与公式错误
- 对发现的错误直接修正
- 输出审查报告供用户确认

## 写作风格

- **先白话后术语**：引入新概念时，先用一句通俗的白话解释"是什么、为什么需要"，再给出正式定义。例如：不要直接说"PagedAttention 将 KV Cache 分为固定大小的 Block"，而是先说"传统方式就像给每个客人预留一整张大桌子，不管来几个人都占着——PagedAttention 换成了拼桌制，按需拼凑，不浪费座位"
- **善用比喻和类比**：对抽象概念用日常生活中的类比来辅助理解（如流水线、快递分拣、图书馆找书等）。比喻应出现在概念首次引入时，后续使用正式术语即可
- **保持技术准确**：比喻是辅助理解的桥梁，不能替代准确的技术描述。每个比喻之后应紧跟严谨的技术解释，确保读者既"看得懂"也"学得对"

## 注意事项

- 不要凭空编造技术细节，对不确定的内容询问用户
- 保持与博客现有文章一致的技术写作风格：简洁、实用、面向实践
- 长文章可在开头添加 `## 目录` 并使用锚点链接
- Emoji 用于两个层面：(1) `##` 级别非编号标题的图标装饰；(2) 正文中的提示标记、表格表头、对比列表等功能性场景。
